# EMIE 权限系统建设方案

> 状态：权限底座、数据范围、关键写接口和高级治理已完成本地实施，待发布验收  
> 形成日期：2026-07-24  
> 适用范围：EMIE 项目、子任务、设计/送审需求、评分、用户、角色、组织架构、通知及系统管理

## 1. 建设目标

权限系统不以“隐藏页面或按钮”为最终目标，而是统一回答：

> 哪个用户，在什么条件下，可以对哪一类数据执行什么操作。

采用 `RBAC 角色权限 + 数据范围 + 条件策略 + 特殊授权` 的组合模型。前端显示只是权限结果，后端接口校验才是安全边界。

统一判断模型：

```text
主体 Subject：用户、角色、部门
资源 Resource：项目、子任务、设计需求、评分、用户、通知
动作 Action：查看、新建、编辑、删除、提交、审核、评分
范围 Scope：本人、参与项目、本部门、指定部门、全部
条件 Condition：项目类型、状态、阶段、创建人、负责人
```

最终授权结果：

```text
角色功能权限
+ 数据范围
+ 当前业务条件
+ 用户临时授权
- 明确禁用
= 是否允许
```

## 2. 核心原则

1. 默认拒绝：未明确授予的权限一律不允许。
2. 前后端一致：前端控制入口，后端对每次请求重新校验。
3. 权限与业务状态分离：拥有“编辑项目”不代表可以编辑已完结项目。
4. 查询即隔离：列表查询在数据库层按数据范围过滤，不先查全量再由前端隐藏。
5. 权限编码稳定：代码只使用稳定英文编码，中文名称可调整。
6. 角色可扩展：新增角色和用户不再要求修改前端、后端硬编码名单。
7. 可解释：必须能说明某用户为什么有权或无权。
8. 可审计、可回滚：权限变化保留差异、操作者、时间、原因和版本。
9. 最小权限：日常权限通过角色授予，特殊权限使用有期限的单独授权。
10. 高危权限独立管理：身份切换、角色配置、全员通知、批量导出等必须二次确认。

## 3. 权限分类

### 3.1 页面访问

- 工作台
- 全部项目
- 渠道定制单
- 公司常规品
- 设计/送审需求
- 我的子任务
- 评分中心
- 用户管理
- 角色管理
- 组织架构
- 系统设置
- 系统通知

无页面权限时不显示导航，直接访问路由返回 403，且不得加载业务数据。

### 3.2 项目操作

按项目类型分别配置：

- 新建、查看、编辑、删除
- 指派负责人
- 添加子任务
- 推进阶段
- 暂停、恢复
- 申请终止、审批终止
- 完结、重新打开
- 导出
- 查看操作日志

### 3.3 子任务操作

- 查看、新建、编辑、删除
- 更换负责人
- 提交或重新提交成果
- 确认完成
- 查看交付与驳回历史
- 查看、下载附件
- 评价子任务

可以进一步限制可操作阶段：设计、设计送审、3D 送审、打样送审、产品宣发、大货。

### 3.4 审核与评分

- 审核哪些项目类型、阶段和数据范围
- 可以给哪些角色或任务评分
- 是否允许评价自己创建的需求
- 是否允许修改已提交评分
- 是否可以提前查看其他评分
- 是否可以查看最终综合分
- 是否可以撤销或重开评分

评分人由后端根据“创建人角色 + 需求类型 + 当前阶段”生成，不在前端写死。

### 3.5 数据范围

每个查看、编辑、审核权限可以配置：

- 仅本人创建
- 仅本人负责
- 本人参与
- 所属项目
- 本部门
- 本部门及下级部门
- 指定部门
- 指定项目类型
- 全公司
- 全部数据

多个角色的允许范围取并集，同时继续受业务状态和明确禁用约束。

### 3.6 系统管理与高危权限

- 用户新增、编辑、停用、删除
- 用户角色分配
- 角色新增、编辑、删除
- 权限配置与版本回滚
- 组织架构配置
- 管理员身份切换
- 系统通知与全员飞书通知
- 飞书同步
- 系统、审计日志
- 数据导入、导出
- 系统配置修改

## 4. 权限编码规范

建议格式：

```text
<资源域>.<资源或类型>.<动作>
```

首批编码示例：

```text
page.dashboard.view
page.scoring.view

project.channel.view
project.channel.create
project.channel.edit
project.channel.terminate

project.regular.view
project.regular.create
project.regular.edit

design_requirement.view
design_requirement.create
design_requirement.deliver

subtask.view
subtask.create
subtask.edit
subtask.submit
subtask.rejection_history.view

scoring.submit
scoring.result.view
scoring.reopen

admin.user.manage
admin.role.manage
admin.permission.manage
admin.identity.switch
admin.notification.broadcast
```

编码一旦用于生产数据便不直接改名；需要调整时新增编码并提供迁移。

## 5. 权限优先级

统一按以下顺序判断：

```text
系统安全限制
    >
用户级明确禁止
    >
角色级明确禁止
    >
用户临时授权
    >
角色允许
    >
默认拒绝
```

补充规则：

- 多角色功能权限取允许并集。
- 多角色数据范围取范围并集。
- 明确禁止优先于普通允许。
- 终止、完结、归档等业务状态限制不能被普通编辑权限绕过。
- 绕过业务限制必须拥有单独的高危权限，并记录操作原因。

## 6. 数据模型

建议新增以下核心表：

```text
permissions
role_permissions
role_permission_scopes
user_roles
user_permission_overrides
permission_policies
temporary_grants
permission_versions
permission_audit_logs
```

关键字段建议：

### permissions

- `code`：稳定权限编码，唯一
- `name`：中文名称
- `module`：权限分类
- `risk_level`：普通、重要、高危
- `enabled`：是否启用

### role_permissions

- `role_id`
- `permission_id`
- `effect`：`allow` / `deny`

### role_permission_scopes

- `role_permission_id`
- `scope_type`
- `scope_value`：指定部门、项目类型等扩展值

### user_permission_overrides

- `user_id`
- `permission_id`
- `effect`
- `reason`
- `created_by`

### temporary_grants

- `user_id`
- `permission_id`
- `scope`
- `starts_at`
- `expires_at`
- `reason`
- `approved_by`

### permission_audit_logs

- 操作者、目标用户或角色
- 变更前后快照
- 权限差异
- 操作原因
- 来源 IP、时间、关联版本

## 7. 后端架构

### 7.1 统一能力服务

建立统一 `PermissionService` / `PolicyEngine`，业务代码不再散落：

```java
if ("admin".equals(user.getRole())) { ... }
```

统一调用形式：

```java
permissionService.require(user, "project.channel.edit", project);
permissionService.can(user, "subtask.create", project);
permissionService.resolveScope(user, "project.channel.view");
```

### 7.2 三层校验

每个写接口必须依次校验：

1. 是否拥有动作权限；
2. 目标数据是否落在权限范围内；
3. 当前业务状态是否允许该动作。

### 7.3 查询过滤

数据范围转换为 Repository 查询条件或 Specification。禁止先查询全部数据后在 JavaScript 中过滤。

### 7.4 能力清单接口

登录后由后端返回当前用户能力：

```json
{
  "permissionVersion": 18,
  "permissions": [
    "project.channel.view",
    "project.channel.create",
    "subtask.submit"
  ],
  "scopes": {
    "project.channel.view": ["department", "participated"],
    "project.channel.edit": ["created_by_me"]
  }
}
```

## 8. 前端架构

前端不得根据角色名称推断权限，只消费能力清单：

- 无页面权限：隐藏菜单并阻止路由进入。
- 无操作权限：隐藏或禁用按钮。
- 有权限但业务状态不允许：禁用按钮并说明原因。
- 请求返回 403：展示可理解的拒绝原因，不只显示通用报错。
- 权限版本变化：自动刷新能力清单和当前页面。

## 9. 权限配置后台

### 9.1 角色基础信息

- 角色名称、标识、说明
- 启用状态、内置角色标记
- 默认首页
- 角色颜色和徽章

### 9.2 功能权限

按业务模块展示权限树，支持模块级全选，但高级配置仍逐项保存。

### 9.3 数据范围

每个权限独立配置范围，例如：

```text
查看渠道定制单：本部门 + 本人参与
编辑渠道定制单：本人创建
审核渠道定制单：本人所属销售项目
```

### 9.4 条件策略

提供可视化策略构建器：

```text
当 项目类型 = 渠道定制单
且 当前用户 = 所属销售
且 项目状态 ∈ 进行中、待确认
允许 编辑项目
```

管理员不直接编辑 JSON 或表达式。

### 9.5 保存前影响分析

保存前展示：

- 影响用户数量
- 新增和移除的权限
- 数据范围变化
- 高危变化
- 是否会导致用户失去当前页面访问权

## 10. 天花板能力

### 10.1 权限预览

选择角色或用户后，直接展示其页面、操作和数据范围。

### 10.2 权限模拟器

选择“用户 + 具体项目 + 动作”，返回允许或拒绝及完整原因链：

```text
允许编辑
来源：销售角色
权限：project.channel.edit
范围：created_by_me
命中条件：该项目创建人为当前用户
业务状态：进行中
```

### 10.3 版本与回滚

每次权限保存生成版本，可查看差异并回滚；回滚本身也进入审计日志。

### 10.4 临时授权

支持开始和到期时间、授权原因、审批人，到期自动失效。

### 10.5 异常检测

- 无用户使用的角色
- 权限过大的普通角色
- 长期未使用的临时授权
- 同时拥有互斥权限的用户
- 高频 403 或越权尝试

## 11. 实时生效与缓存

- 用户或角色权限变化时递增 `permission_version`。
- 前端定期或在关键请求后检查版本。
- 版本变化后刷新能力清单，无需退出登录。
- 停用用户、撤销高危权限应立即生效。
- 后端可以缓存已解析权限，但缓存键必须包含权限版本。

## 12. 审计要求

至少记录：

- 谁修改了哪个角色或用户权限
- 修改前后差异及影响用户
- 谁授予、批准和撤销临时权限
- 管理员身份切换记录
- 全员通知、批量导出等高危操作
- 无权限接口访问尝试

高危操作要求二次确认、填写原因，并可选择发送飞书提醒。

## 13. 分阶段实施计划

### 第一期：统一权限底座

目标：消除新增角色时需要修改多处硬编码的问题。

1. 盘点现有所有页面、按钮、接口和角色判断。
2. 建立权限编码清单和风险等级。
3. 新增权限、角色权限、用户角色及审计基础表。
4. 实现后端统一 `PermissionService`。
5. 提供当前用户能力清单接口。
6. 前端菜单、页面入口和按钮改为读取能力清单。
7. 保留当前角色行为作为初始化默认模板，确保迁移后权限不意外扩大或缩小。
8. 为关键接口补充允许、拒绝和越权回归测试。

验收标准：

- 现有六类角色行为与迁移前一致。
- 新增角色无需修改代码即可配置页面和基础操作。
- 前端隐藏与后端 403 结果一致。

### 第二期：数据范围

1. 支持本人创建、本人负责、本人参与、本部门、下级部门和全部。
2. 项目、子任务、设计需求、评分列表接入数据库层范围过滤。
3. 详情和写接口接入相同范围校验。
4. 增加跨部门、跨项目和直接构造 ID 的越权测试。

验收标准：

- 用户无法通过接口或猜测 ID 获取范围外数据。
- 列表数量、详情权限和写入权限一致。

### 第三期：策略与管理后台

1. 建设角色权限配置页面。
2. 建设数据范围配置。
3. 增加项目类型、状态、阶段条件策略。
4. 增加用户例外权限和临时授权。
5. 保存前展示影响分析。

### 第四期：高级治理

1. 权限预览与模拟器。
2. 权限来源和拒绝原因解释。
3. 权限版本、差异和回滚。
4. 异常权限检测。
5. 飞书审批授权与定期权限复核。

## 14. 第一期具体执行顺序

后续正式开始开发时按以下顺序推进：

1. 输出《现有权限盘点表》，覆盖前端入口、后端接口、当前角色和数据范围。
2. 冻结首版权限编码，不直接开始改页面。
3. 设计数据库迁移及回滚策略。
4. 实现只读能力解析，先与现有行为并行比对，不立即接管权限。
5. 接管一个低风险页面作为纵向样板。
6. 接管项目查看和新建权限。
7. 接管子任务、设计需求和评分权限。
8. 接管管理员与高危权限。
9. 完成全角色回归测试、权限矩阵测试和越权测试。
10. 在有效生产备份后执行迁移，以兼容模式上线。
11. 观察审计和拒绝日志，确认无误后移除旧的角色硬编码。

## 15. 迁移与发布安全

- 第一次上线只新增表和兼容逻辑，不删除现有角色字段。
- 先把当前行为转换为默认角色模板，禁止上线时重置角色权限。
- 新旧权限引擎并行期间记录差异，不因差异直接阻断用户。
- 完成差异验收后再切换为新权限引擎强制执行。
- 所有数据库变更提供 `db/migrations/` 脚本。
- 生产发布前备份数据库并验证恢复点。
- 权限配置、角色管理和身份切换必须保留紧急回滚入口。

## 16. 明确不采用的方案

- 只在前端隐藏菜单和按钮。
- 仅用一个角色字符串覆盖所有权限。
- 在各 Controller 中继续增加 `role == xxx` 判断。
- 所有操作共用一个“可管理”大权限。
- 先查全量数据再前端过滤。
- 允许管理员直接编写策略 JSON。
- 权限变化只能通过退出登录生效。
- 用超级管理员绕过全部业务状态规则且不留审计。

## 17. 当前结论

正式架构基线为：

> 日常能力由角色管理，数据隔离由范围管理，复杂业务由条件策略管理，特殊情况由限时授权管理；所有授权结果可解释、可审计、可实时生效、可回滚。

下一次继续开发时，应先执行“第一期第 1 步：现有权限盘点”，未经盘点和编码冻结，不直接创建零散权限开关。
