# EMIE 通知中心与飞书协同设计

## 1. 目标与不可妥协原则

通知中心覆盖项目、子任务、审核、成果、权限与系统异常的完整生命周期，并同时提供站内通知和飞书通知。

1. 业务上应通知的收件人必须至少获得一条可追溯的站内通知；飞书为可靠外送通道，不因飞书失败丢失站内待办。
2. 合并、摘要、免打扰和限流只能改善展示或额外补充，不能吞掉任务派发、审核待办、交付、驳回、再次交付、逾期等必达事件。
3. 业务写入与通知事件使用同一数据库事务落库；飞书调用不得阻塞业务提交。
4. 每次通知创建、渠道投递、重试、失败、阅读、点击、卡片操作和人工重发必须留独立审计记录。
5. 去重只处理同一业务动作的技术重试，不合并不同项目、不同子任务、不同状态版本或不同再次交付。

## 2. 总体架构

```text
业务服务
  -> NotificationEvent（同事务 Outbox）
  -> NotificationOrchestrator
       -> Notification（站内必达收件箱）
       -> NotificationDelivery（飞书等渠道投递任务）
       -> NotificationAuditLog（不可覆盖审计）
  -> 异步 Delivery Worker
       -> 飞书机器人消息/交互卡片
       -> 重试、退避、死信与管理员告警
```

业务代码只发布领域事件，不能直接拼飞书消息或调用飞书 API。收件人、模板、优先级、渠道和深链均由通知编排器统一处理。

## 3. 事件与收件人矩阵

| 事件 | 典型收件人 | 必达渠道 | 说明 |
|---|---|---|---|
| 项目创建并指定企划 | 指定产品企划 | 站内 + 飞书 | 销售创建项目后通知企划接单 |
| 项目成员/负责人变更 | 新负责人、被移除成员 | 站内 + 飞书 | 记录新旧归属 |
| 企划接单/项目取消/关闭 | 销售及项目参与者 | 站内，重要变更飞书 | 按项目状态动态通知 |
| 子任务派发/改派 | 指定设计师或供应链 | 站内 + 飞书 | 每个子任务独立通知 |
| 子任务接单 | 产品企划 | 站内 | 重要项目可同步飞书 |
| 子任务首次交付 | 产品企划 | 站内 + 飞书 | 包含成果和审核入口 |
| 子任务驳回 | 子任务负责人 | 站内 + 飞书 | 必须携带驳回原因 |
| 子任务再次交付 | 产品企划 | 站内 + 飞书 | `TASK_REDELIVERED`，展示第 N 次交付和上次驳回原因 |
| 渠道定制一审完成 | 销售 | 站内 + 飞书 | 销售进入二审/评分 |
| 公司常规品一审完成 | 管理员 | 站内 + 飞书 | 管理员进入二审/评分 |
| 二审通过/驳回 | 产品企划、子任务负责人、销售等相关方 | 站内 + 飞书 | 依据项目类型与状态解析 |
| 临期/逾期 | 当前待办负责人，必要时上级 | 站内 + 飞书 | 系统自动提醒与升级 |
| 待授权、角色/部门变化 | 相关用户、管理员 | 站内 + 飞书 | 权限与组织治理 |
| 飞书投递长期失败、队列积压 | 管理员 | 站内 + 飞书 | 系统运维告警 |

所有“查看项目”深链统一指向具体项目/子任务/评分页面；通知不以角色名称硬编码收件人，而是通过当前负责人、任务指派、审核阶段、项目类型和成员关系动态解析。

## 4. 幂等与再次交付

通知幂等键：`事件类型 + 业务对象类型 + 业务对象ID + 状态版本 + 收件人ID + 渠道`。

- 设计师交付任务 A、B、C：三个任务 ID 不同，必须分别通知。
- 同一任务首次交付、驳回后再次交付：状态版本不同，必须分别通知。
- 同一事件因事务重试或飞书网络重试重复执行：幂等键相同，只保留一条通知与一次有效投递。
- 再次交付使用独立事件 `TASK_REDELIVERED`；卡片应显示交付次数、上次驳回原因、新成果及审核入口。

## 5. 催办

项目和子任务均提供催办按钮。

- 项目催办：通知当前项目待办负责人；企划接单阶段通知企划，渠道定制二审通知销售，常规品二审通知管理员。
- 子任务催办：通知当前执行负责人；已交付待审核时通知当前审核人而不是原执行人。
- 多负责人：为每位待办人创建独立通知与独立投递记录。
- 已完成、已取消、已关闭的对象禁止催办。
- 权限：项目参与者、项目负责人和管理角色可催办；无关用户不可催办。
- 频率：同一催办人对同一对象 10 分钟内限一次；不同催办人 30 分钟内可在展示层合并，但审计必须保留每次动作。
- 系统临期/逾期催办与人工催办独立标识；长期未处理可按规则升级给负责人或管理员。

## 6. 数据模型

### notification_event

事务型 Outbox。记录领域事件、业务对象、触发人、状态版本、事件载荷、幂等键、创建时间和处理状态。

### notification

站内收件箱。记录收件人、标题、正文、优先级、业务对象、深链、是否强制、已读时间、点击时间和归档状态。

### notification_delivery

渠道投递。记录 `in_app`、`feishu` 等渠道、投递状态、重试次数、下次重试时间、失败原因、渠道消息 ID 和幂等键。

### notification_audit_log

追加式审计。记录通知创建、入队、发送、送达、失败、重试、阅读、点击、卡片交互、催办、管理员重发与配置变更；不得覆盖或删除历史记录。

### notification_preference

用户偏好。普通动态可配置站内/飞书/静默；必达类别不可关闭，仅允许选择飞书不可用时的兜底提示方式。

## 7. 飞书集成

使用企业自建应用机器人向用户 `open_id` 发送交互卡片。用户表需要稳定保存并维护飞书 `open_id` 映射。

- 卡片包含标题、项目/子任务、状态、截止时间、触发人、操作说明及深链。
- 交付、驳回、待审核、催办、临期和逾期使用不同卡片模板。
- 保存飞书 `message_id`，支持更新原卡片状态而非重复发送。
- 卡片交互回调只做验签、鉴权、幂等接收和快速响应；实际业务操作异步执行。
- 同一用户/群聊的 API 限频由 Delivery Worker 控制；失败按退避策略重试，超过阈值进入死信并告警管理员。
- 用户未绑定 open_id、未在应用可用范围、机器人权限不足均记录为可诊断失败，不得丢弃站内通知。

## 8. 站内体验

- 顶部铃铛显示强制待办与未读数。
- 通知中心支持待处理、未读、全部、项目、任务、审核、催办和系统告警筛选。
- 点击通知直达项目详情、任务处理或评分入口，并记录点击审计。
- 使用 SSE 推送新通知；断线后可通过未读查询恢复。
- 支持批量已读、归档、稍后处理和管理员重发；不允许用户删除审计。

## 9. 管理与可观测性

- 管理后台查询通知事件、收件人解析、投递结果、飞书 message_id、重试和失败原因。
- 可按项目、子任务、用户、事件类型、渠道、时间范围筛选审计。
- 指标：待发送数、失败数、重试数、平均投递耗时、飞书限流次数、未读待办、逾期未处理数。
- 管理员可安全重发失败投递；重发产生新审计记录，不覆盖原失败。

## 10. 分期实施

1. **第一步（当前开始）**：通知领域模型、数据库迁移、事务型 Outbox、站内通知基础 API、审计基础。
2. **第二步**：接入项目创建/指定企划、子任务派发、首次交付、驳回、再次交付、两级审核和催办。
3. **第三步**：飞书机器人卡片、Delivery Worker、重试/死信、绑定校验和投递管理。
4. **第四步**：SSE、通知中心 UI、偏好设置、临期/逾期自动催办、升级规则与数据看板。

任何阶段均不得以合并或限流为由删除必达通知；聚合摘要只能作为原始通知之外的补充。
