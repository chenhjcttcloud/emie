# 成长周报 OS 月度评分接入

产品管理系统由后端按月拉取成长周报 OS 的已发布分数。在“设计师月度绩效”中，360 协同分自动填写“协作能力”，周报质量分自动填写“周报考核”；管理员填写考勤等其余信息后保存，产品管理系统按原权重计算当月绩效。

```text
月度绩效 = 任务完成率 × 70% + 360 协同分 × 10%
         + 考勤分 × 10% + 周报质量分 × 10% − 周报额外扣分
```

任务完成率仍由产品系统依据月度所得积分及目标积分自动计算，最高 150 分。成长周报两项分数为 0–100 分，合法的 0 分正常参与计算。及时性额外扣分沿用产品系统现有规则。

## 人员对应

- 产品系统使用 `users.feishu_user_id` 与成长周报 OS 的飞书 `user_id` 对应，同时核对姓名。
- 不使用产品系统登录账号、数据库主键、飞书 `open_id` 或仅凭同名进行匹配。
- 缺少飞书身份、姓名不一致、对应人员不存在或返回数据不完整时，界面显示具体状态。
- 年度汇总沿用已保存的月度记录，不批量请求全年接口。

## 分数使用及历史记录

仅匹配成功且 `status=published`、`isFinal=true` 的当前分数可自动带入。尚未发布、AI 分析中、重评中、重评失败等情况不按 0 分处理；上游 `previousScore` 仅标为旧分参考。

两项自动分在编辑窗口只读。保存时，后端重新查询成长周报分数，忽略浏览器伪造的这两项分值和来源说明。读取来源接口不写入绩效表，不批量改写旧月份。

上游暂不可用或尚未发布时，已有本月产品系统评分可明确显示“沿用本月已保存分”；尚无对应已保存分的月份不能保存不完整的绩效。每次正常保存通过现有操作日志表记录修改前后完整快照，包括总分及分数来源，和绩效保存处于同一事务。并发更新继续使用原有版本校验。

## 后端配置

仅服务端注入以下环境变量，真实令牌不得写入源码、前端或文档：

| 变量 | 用途 |
| --- | --- |
| `GROWTH_OS_BASE_URL` | 成长周报 OS 的 HTTPS 站点根地址 |
| `GROWTH_OS_SCORE_TOKEN` | 成长周报为产品系统签发的独立接口令牌 |
| `GROWTH_OS_ALLOW_LOCAL_HTTP` | 仅 dev/local 隔离测试可设为 true，允许 `growth-os` 容器别名使用 HTTP；生产不启用 |

两项连接配置均为空时，保留原手工评价流程；已配置但连接或鉴权失败时明确显示故障，不降级为手工填写。客户端不跟随重定向，设置连接/请求超时及响应大小限制。

外部接口为 `POST /api/integrations/product-management/monthly-scores`，请求包含 `month` 和至多 100 组 `feishuUserId`、`name`，通过 Bearer 鉴权。产品系统浏览器只访问自身的管理员接口：

- `GET /api/performance/growth-scores?month=YYYY-MM`
- `GET /api/performance/growth-scores/{month}/{userId}`，其中 `userId` 为产品系统内部账号，由后端读取其飞书身份。

此接入不增加数据库字段，无新增迁移。标准生产发布从部署目录的 root:0600 普通文件 `.growth-os.env` 读取两个连接变量，完整校验后注入候选容器，并强制关闭本地 HTTP；配置不进入 Git 或前端。配置变化需要重新启动对应环境应用。生产启用须有针对该次发布的明确授权。
