# EMIE 架构稳定性改造路线图

目标不是追求“最复杂”，而是让每次改动可验证、可回滚、可定位。

## 总原则

1. 保持单体应用，先治理边界，不提前拆微服务。
2. 数据库、文件、外部同步都必须可追踪、可重试、可回滚。
3. 所有异步任务必须幂等，外部服务失败不能阻断核心业务。
4. 先补观测和测试，再做性能优化。

## 第一阶段：稳定性基础

### A. 数据库迁移

- 引入 Flyway，只允许版本化 SQL 变更。
- 为现有生产库建立一次性 baseline，不回放历史建表。
- `dev`/`local` 可自动执行迁移，`prod` 只执行已审核迁移。
- 发布前检查迁移状态，启动后再次验证版本。

当前已完成迁移框架接入、Flyway 10.x（支持 MySQL 8.4）和 `V1` 基线占位；尚未执行任何业务表结构变更。后续第一条真实结构变更从 `V2` 开始。

验收：新环境可从空库启动；生产迁移失败时应用不切换；迁移可记录、可回滚。

### B. 文件服务边界

- 原文件、缩略图、预览缓存分层管理。
- 统一权限校验、源文件定位和响应策略。
- 缩略图失败自动回退原图，并记录失败原因。
- 上传完成后异步预生成缩略图，失败任务可重试。

验收：原图、缩略图、预览权限一致；缓存删除后可自动重建；单张文件异常不影响详情页其他文件。

### C. 飞书同步可观测性

- 记录增量游标、最近成功时间、最近失败时间和失败原因。
- 统计 pending、processing、done、fail 数量及最近一条失败任务。
- 管理后台提供同步状态卡片，不依赖查日志判断健康度。
- 保持全量对账保护：对账失败不执行破坏性全量重刷。

验收：管理员能在页面判断同步是否正常；失败任务可重试；同步游标不会无故回退。

### D. 关键流程测试

- 项目/子任务完整生命周期。
- 驳回、重交、评分和权限切换。
- 文件上传、缩略图、原图、下载。
- 飞书通知失败重试和同步队列恢复。
- 发布脚本预检、候选切换和回滚。

## 第二阶段：数据治理

- 将文件元数据、交付版本、驳回记录从 JSON 逐步拆成独立表。
- 为历史数据提供只新增、不覆盖的迁移脚本。
- 增加文件引用完整性检查和孤儿文件清理报告。

## 第三阶段：性能与扩展

- 缩略图异步预生成和并发限流。
- 评估 MinIO/S3 作为原文件存储。
- Redis 用于缓存、幂等锁和短期任务协调。
- 增加接口耗时、JVM、数据库连接池和队列指标。

## 发布边界

- 每阶段先本地验证，再同步测试环境，最后由明确指令发布生产。
- 数据库迁移、文件目录和应用版本必须分别具备回滚点。
- 本路线图不授权自动修改生产数据或执行全量同步。
